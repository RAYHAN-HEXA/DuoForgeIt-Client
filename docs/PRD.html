1. Product Overview

TechService Hub (TSH) is a two-founder IT & digital-services marketplace for the Bangladesh market. Customers browse a curated service catalog (websites, software projects, UI/UX, pitch decks, documentation, e-commerce, IT consulting), configure a service with priced options, choose which founder should lead the project, pay manually via local payment rails (bKash / Nagad / Rocket / bank transfer), and track the order through a transparent seven-stage delivery pipeline until files are delivered through the dashboard.

The two founders fulfill all work and administer the platform: they review submissions, verify payments, execute projects, upload deliverables, handle revision requests, and manage site content — no third-party workforce.

Product Principles

  • Direct access to the experts — customers pick the founder whose expertise matches the project; no account managers.
  • Transparent milestone tracking — every order exposes a seven-stage pipeline with a full status audit trail.
  • Server-authoritative trust — roles, order state transitions, and pricing are computed and enforced exclusively server-side.
  • Snapshot integrity — catalog edits never mutate historical orders; price/name/option snapshots are frozen at checkout.

3. Users & Roles

RoleWhoCapabilities
CUSTOMERBuyers of servicesBrowse catalog, manage cart, checkout, submit payments, track orders, request revisions, download deliverables, review completed orders, contact support
ADMINThe two co-foundersEverything a customer can do, plus: stats dashboard, order management & assignment, deliverable uploads, payment verification, revision responses, customer management, message inbox, review curation, homepage CMS

There are exactly two roles (CUSTOMER | ADMIN). Roles are written only by provisioning scripts / DB — never accepted from client traffic.

Founder Model

Admin users carry a FounderProfile — the public identity customers see. Each founder has a discipline that gates which catalog services they can lead:

FounderDisciplineCovers
Founder AWEB_SOFTWARE_ECOMMERCEWebsite development, software projects, e-commerce, cloud deployment
Founder BDESIGN_DOCS_UXPresentation design, technical documentation, UI/UX
EitherBOTHIT consulting & cross-discipline services

At checkout the customer picks FOUNDER_A, FOUNDER_B, or AUTO_ASSIGN. The chosen founder is resolved server-side and recorded with a preference source (CUSTOMER_CHOICE | AUTO_ASSIGN | ADMIN_OVERRIDE); admins may reassign internally — the customer is always notified.

6. Order Lifecycle — Seven-Stage Pipeline

SUBMITTED → UNDER_REVIEW → APPROVED → IN_PROGRESS → QUALITY_REVIEW → COMPLETED → DELIVERED, with terminal off-track states REJECTED and CANCELLED.

StageMeaningMay transition to
SUBMITTEDOrder placed, awaiting founder reviewUNDER_REVIEW, REJECTED, CANCELLED
UNDER_REVIEWRequirements being assessedAPPROVED, REJECTED, CANCELLED
APPROVEDAccepted; payment being confirmedIN_PROGRESS, REJECTED, CANCELLED
IN_PROGRESSWork underwayQUALITY_REVIEW, CANCELLED
QUALITY_REVIEWFounder QA before completionCOMPLETED, IN_PROGRESS (rework)
COMPLETEDWork finished, deliverables stagedDELIVERED
DELIVEREDHanded to customer (terminal, success)—
REJECTED / CANCELLEDTerminal, off-track—

Enforcement: transitions are validated server-side (assertTransition against the ORDER_TRANSITIONS matrix in packages/shared) — no client can push an illegal state. Every change appends to OrderStatusHistory (audit trail surfaced as the order tracker UI).

  • Customer cancellation is permitted only while in SUBMITTED or UNDER_REVIEW.
  • Revision requests are permitted in IN_PROGRESS, QUALITY_REVIEW and DELIVERED.
  • The customer-facing order tracker visualizes the seven stages with timestamps.

11. Non-Functional Requirements

Security

  • CORS allowlist (production origins only); Bearer-token auth — no cookies, credentials: false.
  • Server-side role gating (authenticate + requireAdmin middleware); roles never accepted from clients.
  • Per-order ownership checks — customers can only see their own orders/attachments.
  • zod validation on every route; separate stricter rate limiter on auth/contact endpoints.
  • AuditLog on all admin mutations; uniform error envelope without stack-trace leakage.

Architecture & Deployment

  • npm-workspaces monorepo: apps/web, apps/api, packages/shared; shared package is vendored into each app for serverless builds.
  • Node ≥ 24; TypeScript throughout; Prisma migrations with explicit binary targets for Vercel.
  • Web env: NEXT_PUBLIC_API_URL · API env: CORS_ORIGINS (mirrored pair).
  • Vitest suites for API (app, env, domain, money) and shared package.
