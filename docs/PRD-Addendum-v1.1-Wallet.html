20. Changes to PRD v1.0 (Traceability)

1. Summary of the Change

PRD v1.0 uses a per-order manual payment: the customer pays outside the platform and submits a transaction ID against each order, and an admin verifies it. v1.1 replaces this with a wallet-based system, based on the ManagementEwallet reference screens:

  1. The customer deposits money into a personal TSH Wallet (bKash, Nagad, Rocket or Binance) by sending money to the platform's number/address, then submitting the amount + Transaction ID.
  2. An admin approves or declines the deposit. On approval the wallet is credited.
  3. At checkout the customer pays for the order from wallet balance instantly. No per-order TrxID submission.
  4. The customer can request a withdrawal/refund of unused balance, which an admin reviews and pays out.
  5. Every money movement is recorded in an immutable ledger shown in the customer's History page.

Why: one-time verification per deposit instead of per order, faster checkout, simpler refunds (credit back to wallet), clean accounting, and a path to automated gateways later.

4. Scope

In scope (v1.1)

  • TSH Wallet per user (single currency: BDT).
  • Deposits via bKash, Nagad, Rocket and Binance (USDT) with manual admin verification.
  • Pay for orders from wallet; wallet-funded checkout.
  • Withdrawals (refund payout) with admin processing.
  • Immutable wallet ledger, customer History page, CSV export.
  • Admin: deposits queue, withdrawals queue, user wallets, payment Settings, reconciliation report.
  • Notifications for every wallet event.
  • Migration of existing per-order payments.

Out of scope (v1.1)

  • Automated gateway APIs (bKash/Nagad/Binance Pay) — design keeps provider/providerRef hooks.
  • Wallet-to-wallet transfers between customers.
  • Multi-currency balances (Binance deposits are converted to BDT on credit).
  • Interest, cashback or promo credit (reserved for a later release).
  • Mixed payment at checkout (part wallet / part external). Customer must top up the shortfall first.

IDRequirementPriority
LED‑01Every balance change creates one immutable WalletTransaction row. Rows are never updated or deleted. Corrections are made by new compensating rows.MUST
LED‑02Each row stores: type, amount (always positive), direction (CREDIT/DEBIT), balanceBefore, balanceAfter, reference type/ID (deposit, withdrawal, order), actor (user or admin), reason and timestamp.MUST
LED‑03Entry types: DEPOSIT, ORDER_PAYMENT, REFUND, WITHDRAWAL_HOLD, WITHDRAWAL_RELEASE, WITHDRAWAL, FEE, ADMIN_CREDIT, ADMIN_DEBIT, REVERSAL.MUST
LED‑04Invariant: wallet.balance = Σ credits − Σ debits. A nightly job recomputes this for every wallet and alerts on any mismatch.MUST
LED‑05The customer's History page lists ledger entries and request statuses with filters (type, date range, status), pagination and CSV export.MUST
LED‑06Every wallet mutation is written to AuditLog with actor, action, target and payload (extends FR‑29).MUST

7. Core Flows

7.1 Deposit

  1. Customer opens Deposit, picks a method, copies the account number.
  2. Sends money from the external app.
  3. Enters amount + TrxID (+ optional screenshot) and presses Confirm.
  4. Server validates limits and uniqueness and creates the DepositRequest as PENDING.
  5. Admin verifies the money in the real bKash/Nagad/Binance account, then Approves or Declines.
  6. On Approve, inside one transaction: lock wallet row → write DEPOSIT ledger entry → update balance → mark deposit APPROVED → write audit log → create notification.
  7. Customer sees the new balance and the History entry.

7.2 Checkout with Wallet

  1. Customer reviews the cart and chooses the founder (unchanged from v1.0).
  2. Checkout shows total and wallet balance.
  3. Sufficient: Pay with Wallet → order created SUBMITTED + payment PAID + ledger debit, atomically.
  4. Insufficient: Top up shortfall → deposit approved → return to checkout.
  5. The order then follows the 7-stage pipeline.

7.3 Withdrawal

  1. Customer opens Withdraw, chooses method, destination and amount.
  2. System holds the amount (WITHDRAWAL_HOLD).
  3. Admin sends the money externally and marks Paid with the outgoing TrxID.
  4. Ledger finalizes with WITHDRAWAL; customer is notified. If rejected, the hold is released.

7.4 Cancellation Refund

Cancel/reject → server checks amountPaid → REFUND ledger entry → wallet credited → notification.

8. Order Lifecycle Impact

The 7-stage pipeline is unchanged. Payment now interacts with it as follows:

StagePayment rule in v1.1
SUBMITTEDOrder exists only if payment succeeded. No unpaid orders are created.
UNDER_REVIEWFunds are held as PAID. Customer cancel → full refund to wallet.
APPROVED → IN_PROGRESSNo payment step needed (previously "payment being confirmed"). Founder may start immediately.
QUALITY_REVIEW / COMPLETED / DELIVEREDNo payment action. (With PAY‑08 enabled, the final instalment is charged at COMPLETED.)
REJECTED / CANCELLEDAutomatic refund of the net paid amount.

Result: the old gating rule "payment status gates order progression" (FR‑17) is satisfied at order creation, which removes the payment-verification wait from the delivery timeline.

Required database guarantees

  • All balance changes run in a serializable transaction or use SELECT … FOR UPDATE on the wallet row to prevent double-spend under concurrent requests.
  • Unique constraint on (method, normalized TrxID) to stop duplicate credits.
  • CHECK constraints for non-negative balances.
  • Ledger tables have no UPDATE/DELETE privileges for the application role.

12. UX Requirements

  • Keep the visual language of the reference (dark green theme, yellow primary CTA, rounded cards, Bengali labels). Support Bangla and English with a language toggle; all money shown as ৳ 1,234.50.
  • Deposit page: selected method highlighted, copy button gives feedback, inline validation messages, submit button disabled until valid, and a clear "waiting for admin approval" state with an estimated time.
  • Status badges with consistent colors: Pending (amber), Approved/Paid (green), Declined/Rejected (red), Stale (orange), Held (blue).
  • Confirmation modal before any irreversible admin action; decline requires a reason.
  • Empty, loading and error states for every list; mobile-first layout (Bangladesh traffic is mostly mobile) with a bottom-sheet pattern for forms.
  • Accessibility: keyboard navigable, minimum 4.5:1 contrast, status shown by text as well as color.

14. Non-Functional Requirements

  • Consistency: zero tolerance for balance drift; nightly reconciliation job with alerts.
  • Performance: wallet and history pages < 500 ms p95; checkout payment < 2 s p95.
  • Availability: wallet maintenance-mode switch; deposits can still be queued when payments are paused.
  • Backups & recovery: point-in-time recovery on Neon; ledger exportable to CSV daily.
  • Observability: structured logs with request ID, alerts for stale deposits, reconciliation mismatches, and error-rate spikes.
  • Testing: Vitest suites for money math, ledger invariants, concurrency (parallel debits), idempotency, state transitions, permission checks, and migration scripts. Target ≥ 90% coverage on wallet domain code.
  • Serverless note: because Express runs in Vercel functions, all multi-step wallet operations must be single database transactions; no in-memory state or background timers (use scheduled Vercel Cron for reconciliation and stale-deposit flags).

15. Migration Plan

  1. Schema: add new tables and columns (additive only; no destructive change).
  2. Back-fill: create zero-balance wallets for all users; mark existing payments provider = MANUAL.
  3. Open orders in flight: orders with PENDING manual payments continue through the old verification path (read-only admin queue) until resolved; new orders must use the wallet.
  4. Feature flag: WALLET_ENABLED per environment. Roll out to staging, then to the two founders' accounts, then to all users.
  5. Data check: compare totals before/after; run reconciliation; keep the old payments page available read-only for 30 days.
  6. Cut-over: disable POST /orders/:id/payments for new orders; announce to customers in-app.
  7. Rollback: feature flag off restores the legacy flow; wallet balances remain intact and can be refunded manually via the withdrawal process.

17. Acceptance Criteria (Key Scenarios)

  1. A customer submitting the same TrxID twice for the same method gets DUPLICATE_TRX_ID and no second request is created.
  2. Approving a ৳1,500 deposit increases the balance by exactly ৳1,500.00, creates one ledger row with correct before/after balances, and cannot be approved a second time.
  3. Declining a deposit requires a reason, leaves the balance unchanged, and the customer sees the reason.
  4. Two simultaneous checkouts that together exceed the balance: exactly one succeeds, the other returns INSUFFICIENT_BALANCE.
  5. Retrying the same checkout request with the same idempotency key charges once.
  6. Cancelling an order in UNDER_REVIEW refunds the full paid amount to the wallet automatically.
  7. A withdrawal request holds funds immediately; rejection releases them; marking paid finalizes with an outgoing TrxID.
  8. A frozen wallet cannot pay or withdraw but can view history.
  9. A customer cannot read or modify another user's wallet, deposits, or withdrawals (403/404).
  10. The nightly reconciliation job reports zero mismatches on the seed and test datasets.
  11. Every admin action appears in the AuditLog with actor, target and payload.
  12. The Binance deposit stores the USDT amount, the exchange rate used, and the credited BDT amount.

18. Analytics & KPIs to Instrument

Deposit funnel (opened → submitted → approved), median approval time, decline rate by reason, average deposit size, wallet-funded checkout rate, top-up-from-checkout conversion, withdrawal rate and average time to pay out, total wallet liability over time, and reconciliation mismatches.
